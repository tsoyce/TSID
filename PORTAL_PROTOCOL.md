# Манифест портала — договор между SSO и сервисом

**Версия протокола: 1. Появился в SSO v4.1.**

Это спецификация, а не заметки: её реализует код на чужой стороне, в том числе
написанный нейросетью по `integration.md`. Готовый пример с подставленными
данными конкретного портала администратор получает вместе с этим файлом в
карточке портала.

---

## Зачем

Две вещи, обе про то, чтобы человек не пугался и чтобы администратору не
пришлось работать руками.

1. **Роли.** Администратор не должен вбивать карту ролей вручную. Нажал
   кнопку — SSO спросил у сервиса, какие у него роли, и предложил
   сопоставление.
2. **Лицо.** Человек сидит на `site.com`, жмёт «войти» — и попадает на
   `sso.site-id.com`, который выглядит совершенно иначе. Это читается как
   подмена. На «мостике» должны быть оба логотипа и общая стилистика.

---

## Что публикует портал

Один статический файл:

```
GET {base_url}/.well-known/sso-portal.json
Content-Type: application/json
```

```json
{
  "sso_portal": 1,
  "name": "Название сервиса",
  "roles": [
    { "slug": "administrator", "title": "Администратор" },
    { "slug": "editor",        "title": "Редактор" },
    { "slug": "customer",      "title": "Покупатель" }
  ],
  "branding": {
    "accent": "#E4572E",
    "logo": "/assets/logo.png",
    "tagline": "Короткая строка о сервисе"
  }
}
```

Аутентификация не нужна: секретов в файле нет — роли и логотип портал и так
показывает своим посетителям. Требовать её значило бы удвоить работу на чужой
стороне ради нулевой выгоды.

Необязательный блок `users` сообщает, что портал умеет отдавать своих людей:

```json
{
  "users": { "url": "/sso/users.php", "count": 1234 }
}
```

Это только адрес. Ни включить перенос, ни назвать ключ манифест не может —
ключ выдаёт администратор SSO кнопкой, и без него выгрузка не отвечает.

Обязательно только `sso_portal`. Нет `roles` — «ролями не управляю», нет
`branding` — «оформляй как хочешь». Роли принимаются и просто строками, без
`title`: придираться к форме там, где смысл понятен, значит ломать интеграцию
на ровном месте.

---

## Что с этим делает SSO

| Поле | Что происходит |
|---|---|
| `roles` | Запоминаются и показываются администратору. Сопоставление он подтверждает сам |
| `branding.accent` | Красит блок «вы входите в …» на экране входа |
| `branding.logo` | Скачивается один раз, хранится копией, показывается рядом с логотипом SSO |
| `branding.tagline` | Короткая подпись под названием портала |
| `branding.background`, `surface`, `text` (и они же с `_dark`) | Тема экрана входа, когда человек пришёл из портала (v4.65). Каждая тема применяется целиком, если текст на фоне и карточке даёт контраст не ниже 4.5; иначе остаётся родная, а причина видна в карточке портала |
| `branding.accent_dark` | Акцент тёмной темы; без него выводится из `accent` |
| `branding.radius` | Скругление: целое 0–16 px, из него строится шкала |
| `branding.font`, `branding.font_display` | Ключи из списка установки: `golos`, `inter`; для `font_display` ещё `garamond`. Адреса шрифтов не принимаются |
| `branding.wash` | `false` — без подкраски фона акцентом |
| `branding.headline`, `branding.headline_note` | Цитата и подпись в левой панели входа: текст до 160 и 60 знаков. Знак SSO остаётся внизу панели |
| `users.url` | Запоминается адрес выгрузки. Проверяется, что он ведёт на хост самого портала |
| `users.count` | Показывается администратору как масштаб предстоящего переноса |

Обход автоматический: раз в час SSO опрашивает порталы, которых ещё не
спрашивал или спрашивал больше суток назад. Плюс кнопка «Спросить у портала» в
карточке. После неудачи следующая попытка не раньше чем через сутки — портал
без манифеста не должен получать запрос каждый час.

---

## Перенос людей: портал отдаёт, SSO забирает

Модуль — файл `sso/users.php` из набора. Доделать в нём нужно одну функцию:
запрос к своей таблице пользователей. Всё остальное — проверка подписи,
страницы, формат — уже написано.

**Направление.** Спрашивает SSO, отвечает портал. Обратное — «портал сам
присылает своих людей» — выглядит удобнее и не годится: тогда любой, кто
дотянулся до ключа портала, кладёт учётные записи в источник истины по своей
инициативе. Отвечать на вопрос и решать — разные полномочия, и второе остаётся
у SSO.

**Ключ** выдаётся кнопкой в карточке портала и вписывается в его `config.php`
как `users_secret`. Он отдельный от `client_secret`: живёт в другом файле,
отзывается отдельно и, если его сменили, вход при этом не ломается. По проводу
ключ не ходит — уходит подпись.

```
GET {users.url}?limit=200&offset=0
X-SSO-Client:      {client_id}
X-SSO-Timestamp:   1754650000
X-SSO-Signature:   sha256=hmac_sha256("{timestamp}.limit=200&offset=0", users_secret)
```

До версии 4.89 заголовки назывались `X-TSOY-*`. Пока идёт переходный период (до 5.0), они приходят рядом с `X-SSO-*` с теми же значениями, и набор принимает любые.

Портал сверяет подпись через `hash_equals` и отвергает метку времени старше
пяти минут — иначе подслушанный запрос можно повторять вечно. Ответ:

```json
{
  "users": [
    { "id": "1042", "email": "i@example.ru", "login": "ivanov",
      "email_verified": true, "first_name": "Иван", "last_name": "Иванов",
      "phone": "+79990000000", "password_hash": "$2y$10$…",
      "created_at": "2021-03-04 10:00:00", "roles": ["editor"] }
  ],
  "total": 1234
}
```

`id` — внутренний номер пользователя у портала, и он обязателен. По нему SSO
узнаёт того же человека при повторном переносе, даже если тот сменил и почту, и
фамилию. Кроме него нужно хотя бы одно из двух — `email` или `login`.

`password_hash` принимается только как bcrypt (`$2y$…`) или argon2 — они
переезжают как есть и перехэшируются при первом входе. `md5`, `sha1` и открытый
пароль отдавать не надо: SSO их не примет, а человек задаст пароль заново.

`roles` (v4.66) — необязательный список слагов ролей человека у портала, тех же,
что в манифесте. SSO выдаёт по карте ролей портала, а без пары в карте —
одноимённую роль, заведённую за этим порталом; только в области этого портала.
Общие роли SSO перенос не выдаёт никогда (кроме «Админа портала» в его же
области): иначе портал раздавал бы права на весь SSO. Повторный перенос роли
только добавляет.

**Как сводятся люди** — от надёжного признака к слабому:

| Признак | Когда срабатывает |
|---|---|
| Прошлый перенос | пара «портал + внешний номер» уже связана — заведомо тот же человек |
| Почта | совпадение адреса это совпадение человека |
| Логин | **только** если почты нет ни у нас, ни у него: одинаковый логин у разных людей на разных сервисах — обычное дело, и склейка отдала бы одному доступы другого |

Чего перенос не делает: не перезаписывает уже заполненное у SSO (портал —
источник истины о себе, но не о человеке), не трогает пароль, если свой уже
есть, и **не переносит роли** — ими управляет карта соответствия, и менять
доступы переносом нельзя.

## Уровень доступа: что портал получает в токене

Все три поля ниже едут **только со scope `roles`**. Портал, не запросивший его,
не получает ни ролей, ни уровня: ветвиться по правам ему будет не по чему.

Кроме `roles` в токен едут два поля — одно и то же в двух представлениях:

```json
{
  "roles": ["user", "shop:editor"],
  "access_level": 60,
  "access_tier": "editor"
}
```

`access_level` — число 0–99, `access_tier` — его словесное имя. Это **сводка**:
короткий ответ на вопрос «сколько этому человеку можно», чтобы не разбирать
чужой словарь ролей. Число упорядочено, сравнение `>=` осмысленно:

```php
if ($claims['access_level'] >= 70) { /* админские разделы портала */ }
```

Ступени: `0` заблокирован, `10` гость, `20` пользователь, `25` доверенный,
`50` наблюдатель, `55` модератор, `60` редактор, `65` выпускающий,
`70` администратор сервиса, `80` администратор организации, `90`+ уровни SSO.
Промежутки оставлены намеренно: новая ступень между 20 и 50 не сломает уже
написанное сравнение `>= 50`.

**Границы, которые стоит знать:**

- Уровень считается **для вашего портала**. Роли соседних сервисов в него не
  входят: администратор чужого портала приезжает к вам обычным пользователем.
  Глобальные роли провайдера действуют везде — у них область вся установка.
- Уровень **не заменяет вашу проверку**. «У него 70» — повод показать раздел,
  а не основание пустить в него, не спросив собственные правила.
- Уровень **меняется** вслед за ролями. Это не идентификатор: идентификаторы —
  `sub` и номер аккаунта, и они не меняются никогда.
- Портал уровень **не задаёт**. Его назначает провайдер идентичности; что с ним
  делать у себя — решает портал.
- Кому хватает `roles`, может `access_level` игнорировать: поле добавочное,
  ничего не ломает.
- **Пустой `roles` — не «нет прав».** Заведённая карта соответствия отдаёт
  порталу только то, что в ней есть: роль без соответствия не передаётся,
  включая `user`. Отказ портал должен строить на явном признаке — `0` в
  `access_level`, отсутствие своей записи, — а не на пустоте списка.

Разбор, почему уровень — отдельное поле, а не первые цифры номера аккаунта, —
в `ACCESS_MODEL.md` §0.

## Границы

Их стоит прочитать до реализации: они объясняют, почему протокол выглядит
именно так, и экономят время на попытках сделать «побогаче».

### CSS, HTML и скрипты не принимаются

Ни в каком поле, ни в каком виде. Для CSS в схеме SSO нет даже места, и это
проверяется тестом.

Причина не в лени. Произвольный CSS позволяет спрятать логотип SSO, перекрыть
строку с адресом, подменить подписи полей и нарисовать поверх формы что угодно.
Портал А оформился бы под портал Б и собирал пароли от него. Провайдер
идентичности такого позволять не может, каким бы красивым ни выглядел результат.

Вместо разметки портал передаёт **параметры**: цвет, логотип, подпись.
Результат — «братья из одной оперы», поверхность для злоупотреблений нулевая.

### Экран входа остаётся экраном SSO

Логотип портала встаёт **рядом** с логотипом SSO, а не вместо него. Домен,
типографика, вёрстка и тексты формы принадлежат SSO и не настраиваются.

| Портал задаёт | Портал не задаёт |
|---|---|
| свой логотип рядом с нашим | логотип SSO |
| акцентный цвет | шрифты, вёрстку, размеры |
| короткую подпись | тексты формы, названия кнопок |
| — | CSS, HTML, скрипты |

### Роли в SSO по манифесту не заводятся

Портал сообщает, какие роли есть **у него**. Какие роли есть у SSO — решает его
администратор. Иначе чужой сервис пополнял бы справочник ролей провайдера
идентичности.

### Карта соответствия не меняется автоматически

Сопоставление предлагается, но применяет его человек. Карта управляет
доступами: если бы она заполнялась по содержимому чужого файла, смена файла на
той стороне меняла бы права людям.

## Технические ограничения

| Что | Ограничение |
|---|---|
| Схема | только `https` (исключение — `localhost` для разработки) |
| Редиректы | не выполняются: разрешённый хост первым же 302 увёл бы куда угодно |
| Размер манифеста | до 64 КБ |
| Таймауты | 3 с на соединение, 5 с на ответ |
| `accent` | только `#RRGGBB`. `red`, `rgb(…)`, `#fff`, `var(--x)` игнорируются |
| `tagline` | до 120 знаков обычного текста |
| `logo` | до 512 КБ, любой растровый формат, **только с хоста самого портала** |

Логотип **скачивается**, а не берётся ссылкой. Причин две: ссылка на чужой
домен раскрывала бы порталу IP каждого, кто открыл экран входа, включая тех,
кто в этот портал не собирался; и картинку по ссылке можно подменить в любой
момент после того, как её посмотрели. SSO перекодирует изображение через GD —
это заодно убивает всё, что картинкой не является.

## Пример на PHP

```php
<?php
// /.well-known/sso-portal.json
header('Content-Type: application/json; charset=utf-8');
header('Cache-Control: public, max-age=3600');
echo json_encode([
    'sso_portal' => 1,
    'name' => 'Название сервиса',
    'roles' => array_map(
        static fn(string $slug, string $title): array => ['slug' => $slug, 'title' => $title],
        array_keys(ROLES), array_values(ROLES)
    ),
    'branding' => [
        'accent'  => '#E4572E',
        'logo'    => '/assets/logo.png',
        'tagline' => 'Короткая строка о сервисе',
    ],
], JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES);
```

Если роли меняются редко, файл можно просто положить статикой.

---

## Если манифеста нет

Ничего не ломается. Связка работает и без него — просто карту ролей придётся
заполнить руками, а экран входа останется без логотипа портала. Отсутствие
манифеста для SSO — обычное дело, а не ошибка: модуль на той стороне может быть
ещё не написан.
