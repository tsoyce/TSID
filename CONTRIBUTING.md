# Как участвовать

Спасибо за интерес к проекту. SSO — самостоятельный SSO-сервер на PHP без
Composer и node; это накладывает несколько правил, которые стоит прочитать до
первого pull request.

## Запуск локально

```bash
# dev-сервер на SQLite (прод — всегда MySQL)
php -d extension=pdo_sqlite -d extension=sodium -S localhost:8710 -t public public/index.php
# откройте http://localhost:8710 и пройдите инсталлятор, выбрав драйвер SQLite
```

## Тесты

```bash
bash tests/run-all.sh          # всё разом: линт, инсталлятор, юниты, WebAuthn, e2e, смоук
```

Скрипт сам поднимает SSO (:8710) и тестовый портал (:8711) и гасит их после прогона.
Отдельные наборы:

| Файл | Что проверяет |
|---|---|
| `tests/unit.php` | RFC-векторы TOTP и PKCE, JWT (подпись, подделка, `alg=none`), шифрование |
| `tests/webauthn_test.php` | Полный цикл passkey на синтетических векторах + негативные случаи |
| `tests/e2e.php` | Живой OIDC-цикл через сгенерированный PHP-kit, refresh-ротация, backchannel |
| `tests/admin_smoke.php` | Обход всех страниц админки и профиля, загрузки файлов, имперсонизация |
| `tests/install_e2e.sh` | Прогон инсталлятора от приветствия до lock-файла |
| `tools/probe.php` | Мусор на входе: каждый маршрут получает несуществующий номер, ноль, буквы и обход каталога. Плюс два прохода на доступ — без входа и вошедшим без прав. Идёт последним: портит состояние базы |

**PR без зелёной батареи не принимается.** Новая функциональность приносит свои проверки.

## Правила кода

Они не про вкусовщину — каждое закрывает конкретный класс ошибок.

| Правило | Почему |
|---|---|
| Файл ≤ 400 строк | Комфортно читать человеку и генерировать нейросети |
| Только PDO prepared statements | Конкатенация SQL с данными запрещена стилем |
| Сравнение секретов — `hash_equals()` | Тайминг-атаки |
| Экранирование на выходе (`esc()`), не «санитизация» на входе | XSS |
| Токены и секреты не пишутся в логи никогда | В аудит — только хэш-префикс (8 hex) |
| Никаких новых зависимостей | Либо вендорим одним файлом, либо пишем своё на 100–300 строк |
| Ни одной строки с зашитым названием установки | White-label: `Setting::appName()`, `{{APP_NAME}}` |
| Новое ограничение = выключенный по умолчанию тумблер | Принцип опциональности |

Комментарии — на русском, по делу: объясняют «почему», а не пересказывают код.

## Структура

```
public/          единственный webroot
app/Core/        Router, DB, View, Auth, Jwt, Keys, WebAuthn, Totp, Mailer…
app/Models/      слой данных, весь SQL живёт здесь
app/Oidc/        протокол: Discovery, AuthorizeFlow, TokenFlow, EventDispatcher
app/Controllers/ тонкие контроллеры
templates/       SSR-шаблоны, логика не сложнее if/foreach
migrations/      001_init.sql, 002_… — по файлу на изменение
tools/           служебные скрипты разработки (в дистрибутив не попадают)
```

## Массовые правки файлов — только через `tools/rewrite.php`

Однажды разовый скрипт замены обнулил три файла макетов: `preg_replace` не смог
скомпилировать шаблон, вернул `null`, и этот `null` немедленно уехал в
`file_put_contents`. Файлы стали пустыми, страницы отдавали пустой HTML, и
заметилось это далеко не сразу.

Поэтому: любая правка, затрагивающая больше двух-трёх файлов, идёт через
`tools/rewrite.php`. Он отменяет всю операцию целиком, если хоть один файл
даёт пустой результат, ломает синтаксис PHP или получает дубль атрибута в теге
(второй `class=` браузер молча игнорирует — правка «применилась», а эффекта нет).

```php
require 'tools/rewrite.php';
$r = (new Rewrite(['templates']))->skip('/emails/');
$r->dryRun();                       // сначала посмотреть, что изменится
$r->apply(fn($src, $path) => str_replace('было', 'стало', $src));
echo $r->report();
```

Инвариантами занимается `tests/templates_test.php` — он входит в общую батарею
и ловит пустые файлы, сломанный синтаксис, дубли атрибутов, ссылки на
несуществующие ассеты и необъявленные CSS-переменные.

## Что перед PR

1. `bash tests/run-all.sh` — зелёный.
2. Новая миграция? Файл `NNN_название.sql`, плейсхолдеры таблиц в фигурных скобках: `{users}`.
3. Меняли интерфейс? Проверьте на 375px — горизонтального скролла быть не должно.
4. Опишите в PR, какое правило из [ROADMAP.md](ROADMAP.md) §1 закрывает изменение.

## Чего в проект не берём

Список с обоснованиями — в [ROADMAP.md](ROADMAP.md) §4: SPA, Composer в проде,
SAML, микросервисы, массовые действия над пользователями. Если считаете, что
решение устарело — открывайте issue с аргументами, а не PR.
