## 0.1. Решения, которые уже приняты

Четыре вопроса возникают у каждого, кто пишет этот мост. Ответы ниже — не
советы, а часть спецификации: делай так и не спрашивай.

**Оставлять ли свою форму входа по паролю?** Нет. {{APP_NAME}} — единственная
дверь. Политики паролей, блокировки, 2FA и замок по бездействию живут в нём;
вход мимо них означает, что их нет. Форму убери из интерфейса и оставь за
флагом `allow_local_login` в `sso/config.php` — по умолчанию `false`,
включается руками и на время, когда SSO недоступен. Подробно — §4.3.

**Как понять, что человек — администратор?** По claim `roles`; если карту ролей
ещё не завели — по числу `access_level` (`>= 70` администратор сервиса, `>= 55`
модератор). Разбирать префиксы и угадывать по названиям не нужно: администратор
{{APP_NAME}} сопоставляет роли руками, и ты получаешь свои названия. Подробно —
§4.1.

**Что делать с человеком, у которого прав на твоём сайте нет?** Завести
локальную запись с обычной ролью и пустить на публичную часть; в админку — 403.
Не пускать вовсе — не твоё решение: кого допускать до портала, решает
{{APP_NAME}} политикой доступа, и посторонний до `callback.php` не доедет.
Подробно — §4.2.

**Как связать с SSO учётные записи, которые уже есть у тебя?** Поштучно при
входе — по подтверждённой почте (§3, шаг 4). Всех разом, до запуска — выгрузкой
через `sso/users.php` (§11). Логин для сопоставления годится только тогда,
когда почты нет ни у тебя, ни в {{APP_NAME}}.

|---|---|

### Куда именно класть файлы

`sso/` кладётся в **веб-корень** — каталог, на который смотрит `DocumentRoot`.
Для сайта с фронт-контроллером (`public/index.php`) веб-корень — это `public/`,
а не корень проекта: файлы, положенные уровнем выше, просто не отдаются, и
`login.php` ответит 404.

```
проект/
├── app/                  ← сюда НЕ надо
├── public/               ← DocumentRoot
│   ├── index.php
│   └── sso/              ← сюда
└── sso-secrets.php       ← сюда установщик положит секреты (вне веб-корня)
```

Проверка одна: `{{CLIENT_URL}}/sso/login.php` должен открываться.

### Если у сайта уже есть своя сессия

`/sso/*.php` обязаны открывать **её же** — то же `session_name()` и те же
`session_set_cookie_params()`. Для этого в наборе есть `bootstrap.php` с
функцией `sso_session_start()`: подключи в ней бутстрап своего приложения
вместо голого `session_start()`.

Иначе вход окажется в другой сессии: `state` и `nonce` сойдутся, токен
проверится, `$_SESSION['sso_user']` запишется — а приложение его не увидит.
Симптом обманчивый и ошибок не даёт: «вошёл, но я гость».

### Секреты не живут в `config.php`

Файл лежит в веб-корне и, как правило, в git. Установщик кладёт `client_secret`
и `users_secret` отдельным файлом уровнем выше, а `bootstrap.php` подставляет
их поверх. Плейсхолдеры `{{CLIENT_SECRET}}` в `config.php` — нормальное
состояние, а не недоделка.

Спрашивать конфиг нужно **только** через `sso_config()`, а «показывать ли
кнопку входа» — только через `sso_ready()`. Пока «настроен ли вход» и «где
взять секрет» отвечают разные куски кода, они однажды разойдутся, и получится
кнопка, которая на нажатие отвечает «вход не настроен».

## 3. Поток входа

1. `login.php`: сгенерируй `state` (32 hex) и `code_verifier` (43–128 симв.),
   положи ОБА в серверную сессию; `code_challenge = base64url(sha256(verifier))`;
   редирект на `{{ISSUER}}/authorize?response_type=code&client_id={{CLIENT_ID}}&redirect_uri=…&
   scope={{SCOPES}}&state=…&nonce=…&code_challenge=…&code_challenge_method=S256`.
2. `callback.php`: сверь `state` (hash_equals) и, если пришёл, `iss` — он обязан
   быть `{{ISSUER}}` (RFC 9207: чужой `iss` — ответ другого провайдера, код от
   него в наш `/token` не неси) → POST `{{ISSUER}}/token`
   (`grant_type=authorization_code`, `code`, `redirect_uri`, `client_id`,
   `client_secret`, `code_verifier`).
3. Проверь `id_token` ВСЁ обязательно: подпись RS256 ключом из JWKS по `kid`;
   `iss === "{{ISSUER}}"`; `aud === "{{CLIENT_ID}}"`; `exp` в будущем;
   `nonce` совпал с сохранённым.
4. Локальный пользователь — лестница ровно из четырёх ступеней, сверху вниз,
   первое совпадение выигрывает:

   1. **По `sub`** — нашёл, вошёл, конец. `sub` вечен, менять его нельзя ничем.
   2. **По подтверждённой почте** — только если `email_verified === true` **и**
      у тебя ровно одна запись с этим адресом **и** к ней ещё не привязан
      никакой `sub`. Тогда пропиши в неё `sub` — старый аккаунт стал общим.
      Два совпадения, непроверенная почта, уже привязанный `sub` — не трогай,
      это работа для человека.
   3. **По логину (`preferred_username`)** — только когда почты нет ни с одной
      стороны: ни в claims, ни у твоей записи. Если почта есть хоть у кого-то
      из двоих — не сопоставляй. `ivanov` у тебя и `ivanov` в {{APP_NAME}} —
      это, скорее всего, разные люди, а склейка аккаунтов необратима.
   4. **Не нашёл — создай.** Сохрани `sub`, `email` (может не быть), имя.

   НИКОГДА не ищи по одной лишь почте без проверки `email_verified`: почта
   меняется и её можно заявить чужую — это ошибка №1 самодельных интеграций.

   **Claim `email` может отсутствовать.** У части людей почты нет вовсе — их
   перенесли из сервиса, где регистрация шла логином и паролём. Тогда ключа
   `email` в claims нет (не пустая строка — ключа нет). Колонка email у себя
   обязана быть NULL-able, а UNIQUE по ней — допускать NULL, иначе второй такой
   человек не заведётся. Имя для показа бери из `name`, а если и его нет — из
   `preferred_username` (там логин).
5. Создай локальную сессию. Сохрани `sid` из id_token (нужен для logout-событий)
   и `refresh_token`, если запрашивал `offline_access` (в БД, не в cookie).

## 4.1. Права: кто здесь администратор

Три поля про доступ едут **только если в запросе был scope `roles`**. Не
запросил — в токене их нет вовсе, и ветвиться будет не по чему. Проверь, что
`roles` есть в `{{SCOPES}}`, и запрашивай его.

```json
{
  "roles": ["user", "{{CLIENT_SLUG}}:editor"],
  "access_level": 60,
  "access_tier": "editor"
}
```

### Как читать `roles`

Что придёт в списке, зависит от того, завёл ли администратор {{APP_NAME}}
**карту ролей** для этого портала.

**Карта заведена** (так и надо сделать): в списке — твои собственные названия,
без префиксов, ровно те, о которых договорились. Ты сравниваешь строки со
своими константами, и на этом всё:

```php
$roles = $claims['roles'] ?? [];
$isAdmin     = in_array('admin', $roles, true);
$isModerator = in_array('moderator', $roles, true);
```

**Карта пустая** (никто её не заполнил): приезжают внутренние слаги
{{APP_NAME}} — глобальные без префикса (`user`, `admin`, `superadmin`), роли
этого портала с префиксом `{{CLIENT_SLUG}}:` (`{{CLIENT_SLUG}}:editor`).
Не пиши разбор префиксов «на всякий случай» — попроси администратора
{{APP_NAME}} заполнить карту, это делается за минуту в карточке портала. А
чтобы ему было что сопоставлять, опубликуй манифест со списком своих ролей
(§10): тогда он увидит их прямо в форме.

**Пустой `roles` — не «нет прав».** Заполненная карта отдаёт только то, что в
ней есть: роль без соответствия порталу не передаётся, включая `user`. Пустой
список означает «ролей, о которых мы договаривались, у него нет» — то есть
обычный пользователь, а не изгой. Отказ строй на явном признаке (`0` в
`access_level`, отсутствие записи у себя), а не на пустоте списка.

### Как читать уровень доступа

Читай **`access_tier`** — ступень словом. Она не зависит от того, какие числа
мы выберем завтра, и в коде видно, о ком речь:

```php
$tier = (string)($claims['access_tier'] ?? '');
if ($tier === 'service_admin' || $tier === 'org_admin') { /* админка портала */ }
```

**`access_level`** — та же ступень числом. Он нужен, когда сравнение должно
работать «и выше»: ступеней много, перечислять их все в `in_array` неудобно, и
новая ступень такое перечисление сломает, а `>=` — нет.

```php
$level = (int)($claims['access_level'] ?? 0);
if ($level >= 70) { /* админка портала */ }
elseif ($level >= 55) { /* модерация */ }
```

Правило простое: **точное совпадение — по `access_tier`, «не ниже чем» — по
`access_level`.** Строить всю логику на числах не надо: `70` в коде через
полгода не читается, `service_admin` читается.

| Уровень | `access_tier` | Кто это |
|---|---|---|
| 0 | `blocked` | заблокирован |
| 1 | `archived` | удалённый аккаунт |
| 10 | `guest` | гость |
| 20 | `user` | обычный пользователь |
| 25 | `trusted` | доверенный |
| 50 | `observer` | наблюдатель |
| 55 | `moderator` | модератор |
| 60 | `editor` | редактор |
| 65 | `publisher` | выпускающий |
| 70 | `service_admin` | администратор сервиса |
| 75 | `people_admin` | администратор с управлением людьми |
| 80 | `org_admin` | администратор организации |
| 90+ | `sso_observer`, `superadmin`, `owner` | уровни самого {{APP_NAME}} |

Между ступенями оставлены промежутки: новая ступень не сломает твоё `>= 55`.
`access_tier` — то же число словом, для читаемости кода; сравнивать удобнее
число, показывать в интерфейсе — слово.

Три вещи, которые стоит знать:

- Уровень считается **для твоего портала**, а не по всей установке. Человек,
  которого сделали администратором соседнего сервиса, приезжает к тебе обычным
  пользователем — админом он там, а не везде. Глобальные роли {{APP_NAME}}
  (администратор установки) действуют во всех порталах: это не исключение из
  правила, а роль, у которой область — вся система.
- Уровень **не заменяет твою проверку**. «У него 70» — повод показать раздел,
  а не основание пустить в него без твоих собственных правил.
- Уровень **меняется** вслед за ролями, и в старом токене он старый.
  Не кэшируй его дольше сессии; отзыв прав приезжает событием (§5).
  Неизменны только `sub` и `account_number`.
- `0` в живом токене почти не встречается: заблокированный не пройдёт вход
  вовсе, а тем, кто уже вошёл, блокировка приезжает событием `user.blocked`.
  Проверка `$level < 10` — второй пояс, а не первый.

### Порядок перехода: сначала роли, потом переключение

**Ловушка стопроцентная, поэтому вынесена отдельно.** Роль синхронизируется при
каждом входе. Значит действующий администратор портала, которому не выдали роль
в {{APP_NAME}}, после первого же входа через SSO получает 403 в собственной
админке — и войти по старому паролю уже не может, потому что парольный вход
выключен.

Правильный порядок:

1. Раздать роли в {{APP_NAME}} всем, кому нужен доступ. Первому администратору
   роль `client_admin` выдаётся сама — вместе со ссылкой установки.
2. Проверить, что вход через SSO работает и роли приезжают.
3. И только потом выключать парольный вход.

Если всё же заперся: администратор {{APP_NAME}} выдаёт ссылку установки заново
(она же назначает роль администратора портала), либо на время ставится
`allow_local_login = true` в `sso/config.php` — см. §4.3.

## 4.2. Пришёл человек, которому у тебя нечего делать

Обычный случай: сайт закрытый, а вошёл кто-то с уровнем `20` — просто
пользователь экосистемы. Что делать:

**Локальную запись — создать.** Всегда. К ней цепляются сессия, настройки,
история, твои внешние ключи. Состояние «вошёл, но у меня его нет» ломает
всё, что ссылается на пользователя, и отлаживать его тяжело.

**В админку — 403.** По `access_level`, по ролям, по своей таблице прав —
как тебе удобнее. Обычная страница отказа, без выхода из SSO: человек вошёл
успешно, просто раздел не для него.

**Отказывать во входе целиком — не твоё решение.** Кого допускать до портала,
решает {{APP_NAME}}: в карточке портала стоит политика доступа —

- `open` — любой, у кого есть аккаунт в {{APP_NAME}};
- `approval` — по заявке, администратор одобряет;
- `invite` — только по приглашению.

Посторонний при `approval` и `invite` до твоего `callback.php` **не доедет**:
он увидит «Заявка на рассмотрении» или «Вход по приглашениям» на стороне
{{APP_NAME}}. Так что если сайт для сотрудников — попроси поставить `invite`
или `approval`, а не изобретай отказ у себя. Раз человек дошёл до колбэка —
его уже пустили, и твоё дело исполнить, а не пересматривать.

Единственное исключение — `prompt=none` (тихая проверка сессии): там отказ
приезжает обратно к тебе как `error=access_denied`. Обработай его как
«не вошёл», без страницы ошибки.

## 4.3. Старая форма входа по паролю

**Убери её.** {{APP_NAME}} должен остаться единственной дверью, и вот почему:
политика паролей, счётчик неудачных попыток, блокировка, 2FA, замок по
бездействию — всё это живёт в SSO. Вторая дверь мимо них не «дублирует вход»,
а отменяет их: атакующему достаточно ходить в ту, где ничего этого нет.

Аварийный вход всё же нужен — на случай, когда SSO недоступен, а зайти надо.
Делается флагом, а не оставленной формой:

```php
// sso/config.php
'allow_local_login' => false,   // включать руками и ненадолго
```

```php
if (empty($config['allow_local_login'])) {
    header('Location: /sso/login.php');   // формы пароля просто нет
    exit;
}
```

Правила для этого флага: по умолчанию `false`; включается правкой файла на
сервере, а не галочкой в админке (иначе угнанная админка сама себе откроет
запасной вход); каждый вход под ним пишется в твой журнал; после починки SSO
флаг возвращается в `false`.

А первого администратора заводить руками не нужно вовсе. В карточке портала
есть кнопка **«Setup-ссылка для админа портала»** — одноразовая, на 7 дней.
Человек открывает её, входит своим аккаунтом {{APP_NAME}} и получает роль
`client_admin` этого портала. Дальше он приезжает в твой `callback.php` уже с
админскими правами в `roles` и `access_level` 70 — тебе остаётся их прочитать.
Именно эту роль и стоит сопоставить в карте ролей со своим `admin`.

## 5. Backchannel-приёмник ({{BACKCHANNEL_URI}})

SSO шлёт POST с полем `event_token` (JWT RS256 — проверяй подпись/iss/aud как у
id_token, плюс claim `events`). Обрабатывай:
- `logout` — по `sid` погасить локальную сессию. Порталу без манифеста (§ про
  `sso-portal.json`) рядом приходит и стандартный ключ
  `http://schemas.openid.net/event/backchannel-logout` — то же событие для
  готовых библиотек OIDC; обработав `logout`, второй ключ просто пропусти;
- `user.blocked` — закрыть все сессии пользователя по `sub` и не пускать его, пока
  он заблокирован; учётную запись не трогать;
- `user.deleted` — закрыть все сессии по `sub` и **отключить учётную запись**:
  человек, удалённый в SSO, не должен оставаться у тебя живым. Что делать с его
  данными, говорит поле `mode` внутри события (ниже);
- `user.restored` — удаление отменено: включить учётную запись обратно;
- `user.updated` — обновить локальный кэш профиля (имя/email/аватар);
- `access.revoked` — человека убрали из ЭТОГО портала, аккаунт в {{APP_NAME}}
  жив. Закрыть все сессии по `sub`, дальше — по полю `mode`: `closed`
  («Закрыть») — учётную запись в архив, данные не трогать; `removed`
  («Убрать») — стереть учётную запись и её данные. Поля нет ({{APP_NAME}}
  старше 4.64) — только сессии;
- `access.granted` — доступ открыли снова: вернуть из архива того, кого увели
  туда по `access.revoked` с `mode: closed`.
Отвечай `200` быстро, без редиректов и cookies.

### Какое это удаление — поле `mode`

Подробности события лежат под его именем в claim `events`:

```json
{ "sub": "…", "events": { "user.deleted": { "mode": "scheduled", "restore_until": "2026-09-25T10:00:00+00:00" } } }
```

| `mode` | Что случилось | Что делать порталу |
|---|---|---|
| `scheduled` | Удаление отложено: до `restore_until` человек может его отменить | Отключить, данные не трогать. Отменит — придёт `user.restored` |
| `final` | Срок вышел, {{APP_NAME}} обезличил аккаунт | Человек не вернётся: удалить или обезличить данные по своим правилам |
| `purged` | Администратор стёр аккаунт сразу и насовсем | Удалить учётную запись и данные |
| `merged` | Аккаунт слит с другим; `merged_into` — `sub`, под которым человек теперь входит | Перенести записи на `merged_into`, а не удалять |
| поля нет | {{APP_NAME}} старше 4.62 | Как `scheduled`: отключить, ничего не стирать |

Не стирай данные по `scheduled`: удаление в {{APP_NAME}} отменяется ещё две
недели, а стёртое у тебя уже не вернуть.

### Реестр сессий — на твоей стороне

Гасить сессию подменой `session_id()` с `session_destroy()` можно, но работает
это только при файловых сессиях на одном сервере. При Redis, при нескольких
бэкендах или при закрытой `session.save_path` оно **молча не делает ничего** —
и «выйти везде» превращается в кнопку без последствий.

Переносимо и проверяемо — так: своя таблица, в которой видно, чья сессия чья.

```sql
CREATE TABLE sso_sessions (
    php_sid VARCHAR(128) PRIMARY KEY,
    sso_sub VARCHAR(64) NOT NULL,
    sso_sid VARCHAR(64) NULL,
    revoked TINYINT(1) NOT NULL DEFAULT 0
);
```

Готовый файл — `sso/migration.sql.example` в наборе. Дальше:

- при входе — строка с `php_sid`, `sub` и `sid` из токена;
- в приёмнике событий — только `UPDATE … SET revoked = 1` по `sid` (для
  `logout`) или по `sub` (для `user.blocked`, `user.deleted`, `access.revoked`);
- на каждом запросе — проверка `revoked`, и если стоит, сессия закрывается.

Приёмник ничего не гасит сам: он помечает. Гасит приложение — там, где у него и
так есть управление сессией.

## 6. Кнопка входа и виджет

Готовая кнопка — `/sso/sso-button.css`. Файл самодостаточный: ни переменных, ни
шрифтов со стороны, ни зависимостей; цвета уже подставлены под этот экземпляр,
поэтому кнопка выглядит одинаково у всех порталов группы и при этом не тянет
наш дизайн в ваш интерфейс.

```html
<link rel="stylesheet" href="/sso/sso-button.css">

<a class="sso-btn" href="/sso/login.php" data-turbo="false" hx-boost="false">
  <span class="sso-btn-mark">{{MARK}}</span>
  Войти через {{APP_NAME}}
</a>
```

Варианты — классом рядом: `sso-btn-outline` (если ваш фирменный цвет спорит с
акцентом), `sso-btn-dark` (работает на любом фоне), `sso-btn-s` / `sso-btn-l`,
`sso-btn-block` во всю ширину.

Если человек уже входил с этого устройства, назовите его — нажатие станет
подтверждением, а не решением. Имя берите то, что у вас уже есть; запрашивать
его ради кнопки не нужно:

```html
<a class="sso-btn sso-btn-known" href="/sso/login.php" data-turbo="false" hx-boost="false">
  <span class="sso-btn-mark">{{MARK}}</span>
  <span class="sso-known-in"><b>Продолжить как Иван</b><span>i.petrov@example.ru</span></span>
</a>
```

На кнопке стоит имя установки, а не название технологии: человек знает
«{{APP_NAME}}», а не то, на чём это сделано. Если отсылка к провайдеру нужна по
договору — она уходит строкой `sso-btn-note` под кнопку, а не на неё.

### Вход окном поверх сайта

Как открывается вход — окном поверх вашего сайта или всей страницей, —
решает администратор {{APP_NAME}} в карточке портала: «Экран входа» → «Как
открывается вход». Там же включается «Вы вошли» — короткий экран со знаком
портала и именем человека перед возвратом к вам. Вам ничего менять не нужно,
если кнопка работает через `sso.js`:

```html
<script src="{{ISSUER}}/assets/js/sso.js" data-client-id="{{CLIENT_ID}}"
        data-start-url="/sso/login.php" defer></script>
<button class="sso-btn" type="button" data-sso-login>Войти через {{APP_NAME}}</button>
```

**Скрипт — в общем шаблоне сайта, `data-sso-login` — на каждой кнопке
«Войти»**: в шапке, на главной, в меню, на своей странице входа. Кнопка без
атрибута ведёт на вашу страницу входа, и дорога становится длиннее на целую
страницу: главная → ваша `/login` → окно входа. Ссылка остаётся ссылкой — без
скрипта она по-прежнему ведёт на вашу страницу входа:

```html
<a href="/login" data-sso-login>Войти</a>
```

`widget.php` из набора так и сделан. Скрипт спрашивает у {{APP_NAME}}
настройку (`GET {{ISSUER}}/portal/ui?client_id=…` — поэтому в CSP нужен
`connect-src {{ISSUER}}`) и дальше:

- **окном поверх сайта** — окно прямо на вашей странице: затемнение, карточка,
  в ней экран входа {{APP_NAME}} во фрейме, закрывается крестиком и Esc. В конце
  {{APP_NAME}} отдаёт вашей странице адрес возврата с кодом, и она переходит по
  нему — `callback.php` отрабатывает как при входе страницей. Порталу с CSP
  нужен **`frame-src {{ISSUER}}`** — иначе браузер фрейм не покажет, и скрипт
  откроет вход отдельным окном. Вход через сервисы и ссылкой из письма во
  фрейме не работают (их страницы фреймы запрещают) — такой вход продолжается
  отдельным окном сам;
- **отдельным окном браузера** — окно 480×680, а страницу затемняет карточка
  «Окно входа открыто» с кнопками «Показать окно» и «Отмена»: окно легко
  потерять за основным. Затемнение не нужно — `data-overlay="off"` на `<script>`;
- **всей страницей** — обычный переход на {{ISSUER}} и обратно;
- **как решил портал** — как раньше: окно на компьютере, страница на телефоне.

На телефоне вход всегда открывается страницей. Если окно запретил блокировщик,
вход тоже идёт страницей.

Окно на странице и сайт другого домена. Экран входа во фрейме на сайте другого
домена браузер держит на отдельной cookie, изолированной вашим сайтом: вход во
фрейме у такого портала свой, и человек, уже вошедший в {{APP_NAME}} напрямую,
во фрейме вводит пароль ещё раз. Портал на том же домене, что и {{APP_NAME}},
видит общий вход — вошедшему достаточно одного нажатия. Браузер, который не
пускает во фрейм и изолированную cookie, получает кнопку «Открыть окно входа». Старт входа (`data-start-url`) обязан отвечать JSON
`{"authorize_url": "…"}` на запрос с заголовком `X-Requested-With: sso.js` —
`login.php` из набора так и делает. Своему мосту нужно то же самое, а
странице возврата (`callback.php`) — сообщить окну-родителю
`postMessage({type: 'sso:done'}, location.origin)` и закрыться.

Если кнопка стоит внутри формы, скрипт отправляет на старт входа поля этой
формы (строкой `application/x-www-form-urlencoded`) — так до старта доезжает
CSRF-токен портала, и снимать защиту с маршрута не нужно. Кнопка вне формы —
POST пустой, только с заголовком.

Встраивать экран входа {{APP_NAME}} может только ваш портал — адреса из его
карточки — и только пока идёт вход: всё остальное, от личного кабинета до
админки, во фрейм не пускается, как и раньше.

### Сразу через сервис: `idp_hint`

Страницы Яндекса, VK и других сервисов во фрейм не пускают. Поэтому щелчок
«Продолжить с Яндекс ID» в окне поверх сайта уводит саму вкладку прямо на
Яндекс, без лишних окон: скрипт добавляет к адресу входа `idp_hint=yandex`.
Вход кончается переходом на ваш адрес возврата в той же вкладке, как и
обычный. Своя кнопка на портале («Войти через Яндекс») делается
так же — допишите к адресу `/authorize` параметр `idp_hint` с именем сервиса:
`telegram`, `yandex`, `vk` или `github`. Экран выбора человек не увидит.

Работает, только если сервис включён в {{APP_NAME}} и показывается на
экране входа вашего портала. Во фрейме (`display=frame`) подсказка не
действует. В остальных случаях она молча не срабатывает, и человек видит
обычный экран входа.

### Сайт на htmx, Turbo или Livewire — кнопка «молчит»

Если страница «ускорена» (`hx-boost` на `<body>`, Turbo Drive, `wire:navigate`),
переход по ссылке и отправка формы уходят фоновым запросом. Ответ старта входа —
302 на {{ISSUER}}; фоновый запрос упирается в CORS, и на экране не происходит
ничего: ни перехода, ни ошибки.

Поэтому на кнопке уже стоят `data-turbo="false"` и `hx-boost="false"` — они
возвращают обычный переход, а на сайте без ускорителей ничего не делают. Если
вход у вас начинается формой (`<form method="post" action="/sso/login.php">`),
поставьте те же два атрибута на форму. В Livewire не вешайте на кнопку
`wire:navigate`.

### Строгая политика безопасности (CSP)

В виджете нет ни одного `onclick=` и ни одного атрибута `style`: там, где CSP
запрещает inline, такой обработчик не выполняется — и меню не открывается
молча, без ошибки в консоли. Оформление живёт в `sso-button.css`, поведение —
в `sso-widget.js`.

Разрешить порталу нужно четыре директивы, а если вход начинается формой — пять:

```
script-src  'self' {{ISSUER}}    ← sso.js для входа без ухода со страницы
img-src     'self' {{ISSUER}}    ← аватары
connect-src 'self' {{ISSUER}}    ← проверка сессии
frame-src   'self' {{ISSUER}}    ← вход окном поверх сайта (экран входа во фрейме)
form-action 'self' {{ISSUER}}    ← если вход начинается формой: Chrome сверяет
                                   с этим списком и адрес, куда форму уводит 302,
                                   и без SSO в списке молча не переходит
```

Если у сайта есть nonce — пометьте им подключение `sso-widget.js`.

### Что делать, когда сломалось через месяц

Проверка связи на экране настроек — `sso/admin.php` (§12) — отвечает без
единого секрета: откуда взят секрет, принимает ли его {{APP_NAME}}, знает ли он
адрес возврата, сходятся ли часы, отдаётся ли манифест, отвечает ли приёмник
событий, перечитывает ли OPcache файлы (иначе правка `config.php` не
применяется до перезапуска PHP). Вход сломан и экрана не видно — то же с
сервера: `php sso/admin.php check`.

`widget.php`: не вошёл → кнопка «Войти через {{APP_NAME}}»; вошёл →
аватар+имя+меню (Профиль → {{ISSUER}}/profile, Выйти → /sso/logout.php).
Desktop: popup через {{ISSUER}}/assets/js/sso.js
(`<script src="{{ISSUER}}/assets/js/sso.js" data-start-url="/sso/login.php" defer>`
и кнопка с атрибутом `data-sso-login`); фоллбек — обычный редирект.

## 7. Безопасность — нарушать нельзя

state/verifier — только в серверной сессии; сравнение — hash_equals; токены не
логируются; client_secret не попадает в браузер/git; все SQL — prepared;
HTTPS обязателен.

## 8. Чеклист приёмки

- [ ] Вход с нуля создаёт локального пользователя с sub
- [ ] Повторный вход находит его по sub (email в БД менялся — вход не ломается)
- [ ] Человек без почты (`email` в claims отсутствует) заводится и входит
- [ ] Старый локальный аккаунт с той же подтверждённой почтой привязался, а не
      задвоился; с неподтверждённой — НЕ привязался
- [ ] Подделка state/nonce → отказ
- [ ] «Выйти везде» на SSO гасит локальную сессию (≤ минуты)
- [ ] Блокировка в SSO выкидывает из портала
- [ ] Удалённый в SSO человек отключён у тебя (`user.deleted`), данные стёрты
      только при `final` / `purged`; отменивший удаление снова включён (`user.restored`)
- [ ] «Закрыть» в SSO (`access.revoked`, `mode: closed`) выкидывает и уводит учётную
      запись в архив; «Убрать» (`mode: removed`) стирает её; открытый снова доступ
      (`access.granted`) возвращает из архива
- [ ] Есть экран настроек SSO (§12): секрет клиента вводится и проверяется у
      {{APP_NAME}} до сохранения, ключ переноса вводится отдельно, секреты не видны
- [ ] Проверка связи на нём зелёная; когда вход сломан, та же проверка — из консоли
- [ ] client_secret отсутствует в клиентском коде и в git
- [ ] Пользователь с `access_level` 20 входит, видит публичную часть и получает
      403 в админке — не белый экран и не бесконечный редирект
- [ ] Пустой `roles` не превращает человека в изгоя (см. §4.1)
- [ ] Формы входа по паролю в интерфейсе нет; при `allow_local_login = false`
      прямой заход на неё уводит на `/sso/login.php`

## 9. Частые ошибки

Сначала — три симптома, которые не выглядят ошибками и потому съедают больше
всего времени:

| Что видно | Что на самом деле |
|---|---|
| **Кнопка входа есть, а нажатие говорит «вход не настроен»** | «Показывать ли кнопку» и «где взять секрет» отвечают разные куски кода. Спрашивать надо только `sso_ready()` и `sso_config()` (§2) |
| **Вход прошёл, но приложение считает меня гостем** | Кит открыл свою сессию, а не сессию сайта. Чинится в `bootstrap.php` → `sso_session_start()` (§2) |
| **Владелец получил второй аккаунт вместо своего** | Локальную запись искали только по почте. Лестница из §3 — четыре ступени, и для владельца установки есть отдельная (шаг 3.5) |

Дальше — обычные ошибки протокола:

`invalid_grant` — code протух (60 с)/повторно использован/verifier не тот.
`redirect_uri_mismatch` — URI не совпал ПОБАЙТОВО с зарегистрированным.
`invalid_client` — секрет неверен или потерян. Подпись не сходится — обнови JWKS-кэш.
`state mismatch` — чаще всего это F5 или «назад» на странице возврата: `state`
одноразовый. Не пугай текстом ошибки, дай ссылку «войти заново».
**Токен протух сразу после выдачи** — разошлись часы. Проверь NTP на своём
сервере; расхождение больше минуты ломает проверку `exp`, и подсказки об этом
нет ни в одном сообщении.

**«Адрес возврата не совпадает»** — сервис прислал `redirect_uri`, которого нет
в карточке портала. Сравнение байт-в-байт: `/sso/callback` и `/sso/callback.php`
— разные адреса. Угадывать его {{APP_NAME}} не станет, но присланный адрес
запомнит и покажет администратору в карточке портала — добавляется одной кнопкой.

## 10. Манифест портала — чтобы SSO знал вас в лицо

Один статический файл. Он решает две задачи, обе про то, чтобы человек не
пугался и чтобы админу не пришлось вбивать роли руками.

Опубликуйте по адресу `{{CLIENT_URL}}/.well-known/sso-portal.json`:

```json
{
  "sso_portal": 1,
  "name": "{{CLIENT_NAME}}",
  "roles": [
    { "slug": "administrator", "title": "Администратор" },
    { "slug": "editor",        "title": "Редактор" },
    { "slug": "customer",      "title": "Покупатель" }
  ],
  "branding": {
    "accent": "#3B82F6",
    "logo": "/assets/logo.png",
    "tagline": "Короткая строка о сервисе"
  },
  "users": { "url": "/sso/users.php", "count": 1234 }
}
```

Отдавайте с заголовком `Content-Type: application/json`. Аутентификация не
нужна: секретов в файле нет.

### Сначала проверьте, что его вообще отдают

Почти в каждом закалённом конфиге есть правило, режущее всё, что начинается с
точки, — и манифест под него попадает. Отдаётся 403, никакой ошибки нигде не
появляется, и выглядит это как «просто не настроили»: ролей нет, логотипа на
экране входа нет, перенос людей недоступен.

```apacheconf
# Apache (.htaccess): точечные файлы закрыты — кроме .well-known.
# Проверено на живом портале: без исключения Apache отвечал 403.
<FilesMatch "^\.(?!well-known$)">
    Require all denied
</FilesMatch>
```

Если запрет у вас сделан правилом `RewriteRule`, режущим пути с точкой, поставьте
прямо перед ним `RewriteCond %{REQUEST_URI} !^/\.well-known/`.

```nginx
# nginx: сертификатам — только их каталог, остальное — приложению.
location ^~ /.well-known/acme-challenge/ { allow all; }
# общий запрет на точечные пути — с исключением для .well-known
location ~ /\.(?!well-known/) { deny all; }
```

Не оставляйте в конфиге блок, который забирает весь `/.well-known/` себе
(`location ~ /.well-known` или `location ^~ /.well-known/` без `proxy_pass`):
он отдаёт такие пути с диска, и манифест, который собирает приложение, получает
404 от самого nginx. Именно так настраивают сайты шаблоны BrainyCP. Если у вас
эта панель, строку придётся поправить руками — и проверить снова после каждой
пересборки конфига панелью.

Проверка — одной командой, ожидается `200` и `application/json`:

```bash
curl -i https://ваш-домен/.well-known/sso-portal.json
```

Установщик (`sso/install.php`) делает эту проверку сам и говорит прямо, если
манифест не отдаётся.

### Что с этим делает {{APP_NAME}}

**`roles`** — список ролей, которые есть у вас. {{APP_NAME}} их запомнит и
покажет администратору, чтобы тот сопоставил их со своими ролями. Сопоставление
он подтверждает руками: карта ролей управляет доступами, и менять её по
содержимому вашего файла было бы неправильно.

**`users`** — адрес выгрузки ваших людей и сколько их. Нужен только если
переносите существующую базу (§11); нет ключа — {{APP_NAME}} просто не
предложит перенос.

**`branding`** — ваше лицо на экране входа. Человек, нажавший «войти» у вас,
попадает на домен {{APP_NAME}}; если экран выглядит совершенно иначе, это
читается как подмена. Ваш логотип, цвет и подпись встанут рядом с нашими, и
переход перестанет пугать.

**Обложка на витрине** — не в манифесте, а там же, где её ищет любой
мессенджер: картинка превью ссылок на вашей главной,
`<meta property="og:image" content="/img/cover.png">` (подойдёт и
`twitter:image`). {{APP_NAME}} раз в сутки берёт её для карточки вашего
проекта на своей главной и отдаёт свою копию. Лучше 1200×630, до 5 МБ, JPEG,
PNG или WebP; с вашего домена или по https. Нет картинки — карточка
рисуется в вашем цвете с вашим знаком. Своя картинка администратора
{{APP_NAME}} главнее вашей.

### Границы — чтобы не тратить время зря

- **CSS, HTML и скрипты не принимаются.** Ни в каком поле, ни в каком виде.
  Произвольный CSS позволил бы спрятать логотип {{APP_NAME}} и нарисовать
  поверх формы что угодно — то есть оформить страницу входа под чужой сервис.
  Передавайте параметры: цвет, логотип, подпись.
- **`accent`** — только шестизначный hex вида `#3B82F6`. `red`, `rgb(...)`,
  `#fff` и `var(--x)` игнорируются.
- **`logo`** — путь или полный адрес **на вашем же домене**. {{APP_NAME}}
  скачает картинку один раз и будет отдавать свою копию: ссылка на ваш домен
  раскрывала бы вам IP всех, кто открыл экран входа. Формат любой растровый,
  до 512 КБ; вписывается в квадрат 128×128.
- **`tagline`** — до 120 знаков обычного текста.
- Роли в {{APP_NAME}} по этому файлу **не заводятся**. Вы сообщаете, что есть
  у вас; что есть у {{APP_NAME}} — решает его администратор.

### Экран входа в вашем оформлении

Хотите, чтобы вход выглядел как ваш сайт, — пришлите тему в том же блоке
`branding`. Форма остаётся на {{APP_NAME}} (пароль видит только он, работают
ключи доступа, 2FA и единый вход), а цвета, шрифты и левая панель — ваши:

```json
"branding": {
  "accent": "#A53718",      "accent_dark": "#FF8054",
  "background": "#F1ECDC",  "background_dark": "#16171A",
  "surface": "#FFFFFF",     "surface_dark": "#1E1F23",
  "text": "#0E0B07",        "text_dark": "#F4F4F0",
  "radius": 6,
  "font": "inter",          "font_display": "garamond",
  "layout": "left",
  "headline": "Короткая цитата для левой панели входа",
  "headline_note": "— подпись под ней"
}
```

- **`background`, `surface`, `text`** (фон страницы, карточка, текст) — только
  вместе и только hex. Тема применяется целиком, если текст на фоне и на
  карточке даёт контраст не ниже 4.5; иначе остаётся родной вид, а причину
  администратор видит в карточке портала. Тёмная тема (`_dark`) обязана быть
  тёмной: текст светлее фона. Приглушённый текст, рамки полей, текст на кнопке
  и подкраску фона {{APP_NAME}} выводит сам — с той же гарантией контраста.
- **`radius`** — целое 0–16 px. **`font`** — `golos`, `inter` или `system`
  (шрифт устройства); **`font_display`** (цитата и заголовки панели) — ещё и
  `garamond`. Адрес
  своего шрифта прислать нельзя: чужой адрес раскрыл бы вам каждого, кто открыл
  экран входа. Нужен другой шрифт — попросите администратора {{APP_NAME}}.
- **`wash`** — `false`, если подкраска фона акцентом не нужна.
- **`layout`** — где панель: `left` (слева от формы, по умолчанию), `right`
  или `none` — только форма.
- **`headline`**, **`headline_note`** — текст до 160 и 60 знаков для левой
  панели. Знак {{APP_NAME}} стоит внизу панели и в связке над формой — убрать
  их нельзя: экран входа обязан оставаться узнаваемо экраном SSO.

То же самое администратор {{APP_NAME}} может задать и сам — в разделе «Экран
входа» карточки портала, с живым предпросмотром. Там же — обложка панели и
состав способов входа, которых в манифесте нет. Что действует — присланное
вами или заданное там, — решает он; раздел отдаёт и готовый блок `branding`,
если хотите держать оформление у себя.

### Пример на PHP

```php
<?php
// {{CLIENT_URL}}/.well-known/sso-portal.json
header('Content-Type: application/json; charset=utf-8');
header('Cache-Control: public, max-age=3600');
echo json_encode([
    'sso_portal' => 1,
    'name' => '{{CLIENT_NAME}}',
    // Отдайте реальные роли своего приложения
    'roles' => array_map(
        static fn(string $slug, string $title): array => ['slug' => $slug, 'title' => $title],
        array_keys(ROLES), array_values(ROLES)
    ),
    'branding' => [
        'accent'  => '#3B82F6',
        'logo'    => '/assets/logo.png',
        'tagline' => 'Короткая строка о сервисе',
    ],
], JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES);
```

Файл можно и просто положить статикой, если роли меняются редко.

### Проверка

Администратор {{APP_NAME}} нажмёт «Спросить у портала» в карточке — и увидит
ваши роли. Если файл не отдаётся, ничего не сломается: связка работает и без
него, просто карту ролей придётся заполнить руками, а экран входа останется
без вашего логотипа.

## 11. Перенос ваших людей в {{APP_NAME}}

Это ответ на вопрос «а что делать с теми, кто у нас уже зарегистрирован». Два
пути, и они не спорят друг с другом.

**Поштучно, само собой.** Ничего делать не нужно. Человек нажимает «Войти
через {{APP_NAME}}», заводит там аккаунт на ту же почту, возвращается — и
`callback.php` по лестнице из §3 привязывает его к вашей старой записи. Годится,
когда людей немного или база всё равно оживает медленно.

**Списком, заранее.** {{APP_NAME}} забирает вашу базу целиком, и люди входят
уже своими прежними паролями. Файл `sso/users.php` из набора — про это; в нём
дописать нужно **одну функцию** `sso_export_users()`, запрос к вашей таблице.
Проверка подписи, страницы и формат ответа уже написаны, трогать их не надо.

Порядок такой:

1. Администратор {{APP_NAME}} выдаёт **ключ переноса** кнопкой в карточке
   портала. Ключ отдельный от `client_secret`: живёт в другом файле, отзывается
   отдельно, и его смена не ломает вход.
2. Ключ вписывается в `sso/config.php` как `users_secret` (в наборе, скачанном
   после выдачи ключа, он уже подставлен).
3. Адрес выгрузки объявляется в манифесте: `"users": { "url": "/sso/users.php" }`.
4. Администратор нажимает «Забрать людей». {{APP_NAME}} приходит к вам сам.

Запрос выглядит так:

```
GET /sso/users.php?limit=200&offset=0
X-SSO-Client:      {{CLIENT_ID}}
X-SSO-Timestamp:   1754650000
X-SSO-Signature:   sha256=hmac_sha256("{timestamp}.limit=200&offset=0", users_secret)
```

До версии 4.89 заголовки назывались `X-TSOY-*`. Пока идёт переходный период (до 5.0), они приходят рядом с `X-SSO-*` с теми же значениями, и набор принимает любые.

Ответ — страница JSON:

```json
{
  "users": [
    { "id": "1042", "email": "i@example.ru", "login": "ivanov",
      "email_verified": true, "first_name": "Иван", "last_name": "Иванов",
      "phone": "+79990000000", "password_hash": "$2y$10$…",
      "created_at": "2021-03-04 10:00:00", "roles": ["editor"] }
  ],
  "total": 1234
}
```

Что важно в этом ответе:

- **`id`** — ваш внутренний номер, обязателен. По нему {{APP_NAME}} узнаёт того
  же человека при повторном переносе, даже если он сменил и почту, и фамилию.
  Номер обязан быть постоянным.
- Кроме него нужно **хотя бы одно из `email` или `login`**: иначе человека не
  по чему узнавать и строка будет пропущена.
- **`password_hash`** отдавайте, только если это bcrypt (`$2y$…`) или argon2
  (`$argon2id$…`) — их {{APP_NAME}} примет как есть и перехэширует при первом
  входе. md5, sha1 и тем более открытый пароль отдавать не надо: они не будут
  приняты, человек просто задаст пароль заново.
- Страница — до 200 человек, за один заход {{APP_NAME}} заберёт не больше 5000.
  Остальных — следующим заходом.
- **`roles`** — необязательный список слагов ролей человека **у вас**, тех же,
  что в манифесте (`["editor"]`). {{APP_NAME}} выдаст роль по карте ролей
  портала, а если пары в карте нет — одноимённую роль, заведённую за вашим
  порталом. Только в пределах вашего портала: общие роли {{APP_NAME}} через
  перенос не выдаются. Повторный перенос роли только добавляет и ничего не
  снимает; слаги без пары администратор увидит в итоге переноса.

Три правила, которые в файле уже соблюдены, — не ломайте их, дописывая своё:

- **Спрашивает {{APP_NAME}}, отвечаете вы.** Обратное — «портал сам присылает
  своих людей» — выглядит удобнее и не годится: тогда любой, кто дотянулся до
  ключа, кладёт учётные записи в источник истины по своей инициативе.
- **Подпись сверяется через `hash_equals`** по **сырой строке запроса**, а
  метка времени старше пяти минут отвергается: иначе подслушанный запрос можно
  повторять вечно. Границы (`limit` не больше 500) применяются ПОСЛЕ проверки:
  подписано было то, что прислали, и считать подпись по уже обрезанным
  значениям — верный способ получить «подпись не сошлась» на запросе, с которым
  всё в порядке.
- **Только https.** Файл отдаёт персональные данные; по открытому каналу его
  читает кто угодно по дороге.

Как {{APP_NAME}} сопоставляет присланное со своими людьми: сначала по вашему
`id` (если этого человека уже переносили), затем по почте, и только потом по
логину — причём по логину лишь тогда, когда почты нет ни с одной стороны. То же
правило, что и у вас в §3, и по той же причине: однофамильцы не должны
склеиться в одного человека.

## 12. Обязательные экраны портала

У каждого портала на {{APP_NAME}} есть три экрана администратора. Набор кладёт их
готовыми — `sso/admin.php` и `sso/checks.php`; портал, собранный без набора,
делает их сам, по этому разделу. Без них первый же перевыпуск секрета
заканчивается правкой файла на сервере, а «почему не входит» — гаданием.

Открывает их только администратор этого портала: `access_level >= 70` или своя
проверка портала. Значения секретов не показываются никогда — только «есть» и
длина; поля ввода скрытые.

### Настройки SSO — мост

- Показать: издатель, `client_id`, адрес возврата, адрес после выхода, области.
- **Ввести секрет клиента.** Перед сохранением проверить его у {{APP_NAME}}:
  `POST {{ISSUER}}/token` с `grant_type=authorization_code`, заведомо негодным
  `code`, своим `client_id` и введённым секретом. Ответ `invalid_client` —
  секрет не тот, **не сохранять**: вход продолжит работать на старом. Любая
  другая ошибка (`invalid_grant`) — секрет принят. Так опечатка при вставке не
  ломает вход всем.
- Хранить вне веб-корня и вне git (§2, «Секреты не живут в `config.php`»).

### Перенос людей — ключ

- **Ввести ключ переноса** (`pusec_…`, выдаётся в карточке портала: «Забрать
  людей»). Поле отдельное: ключ переноса и секрет клиента — разные вещи, и
  значение не того вида стоит отвергнуть сразу.
- Проверить подписанным запросом к своей выгрузке (§11): `200` — подпись сошлась.

### Проверка связи

Кнопка «Проверить» и таблица: состояние (**есть** / **не всё** / **нет**), что
проверяли, подробности. Ходит к издателю и к самому себе, ничего не сохраняет.
Обязательные строки:

| Что проверять | Как | «есть», когда |
|---|---|---|
| Настройки заполнены | issuer и `client_id` | оба на месте |
| Секрет клиента на месте | длина и откуда взят | есть и лежит вне веб-корня |
| Издатель принимает секрет | `POST /token`, как выше | не `invalid_client` |
| Области запрошены | scopes | есть `roles` |
| Адрес возврата совпадает с сайтом | `redirect_uri` против адреса, каким сайт виден снаружи | побайтно |
| Discovery издателя | `GET {{ISSUER}}/.well-known/openid-configuration` | 200 и `iss` = issuer |
| Ключи подписи | `GET {{ISSUER}}/jwks.json` | 200, ключи есть |
| Издатель знает адрес возврата | `GET /authorize` с вашим `client_id` и `redirect_uri`, без сессии | 302; 400 — адреса нет в карточке портала |
| Часы сходятся | заголовок `Date` издателя | расхождение не больше 60 с |
| Манифест портала | `GET /.well-known/sso-portal.json` | 200, роли перечислены |
| Приёмник событий отвечает | `POST` на backchannel без токена | 400 «event_token required» |
| Обработчик удаления | §5 | не заглушка |
| Ключ переноса, выгрузка отвечает | подписанный запрос к выгрузке (§11) | 200 |

Когда вход сломан, экрана не видно, а нужен он как раз тогда. Поэтому то же —
из консоли сервера. В наборе: `php sso/admin.php check` — проверка,
`php sso/admin.php secret` и `php sso/admin.php users-key` — ввод с клавиатуры,
а не аргументом, чтобы секрет не остался в истории команд.
